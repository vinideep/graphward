# Efficiency measurement protocol

This is a measurement protocol and implementation foundation. No real experiment results, coding-accuracy improvement, token savings, native-host coverage, or release qualification have been established. Synthetic tests exercise the accounting rules only. The separate evaluator always emits `releaseQualification: false` and `improvementClaim: false`, including for complete held-out records. The existing release evaluator and its accuracy threshold remain separate.

## Freeze before collection or tuning

Register the experiment, task identities, requests, source snapshots, seeds, model/version, host/version, tool policy, token/time budgets, sampling conditions, commands, allocation rules, and arm artifact hashes before running it. Use exactly three arms: `baseline`, `current`, and `simplified`. Each arm runs the same task from the same source snapshot; its candidate/configuration artifact hash can differ. Pair by task ID, repository, source revision, model, model version, request hash, seed, and repetition. Never pair by the arm artifact hash.

Freeze development and held-out membership before the pilot or tuning. Every repository/task ID must be unique across the entire frozen task set: seed, request, or model variants cannot inflate distinct task counts or cross splits. Freeze the held-out task count, repetitions, task-selection manifest hash, precision/power assumptions and decision policy at that time. A nonempty size justification is required in the specification, but this field alone does not establish statistical adequacy. No actual held-out sample size or statistical power has been established by the synthetic fixtures in this repository.

The directional pilot is **12 development tasks across at least 2 repositories × 3 arms × 3 repetitions = 108 task-run observations**. This is a variance/completeness pilot, not an efficacy or release test. Repetitions are clustered within each task: 108 observations do not constitute 108 independent tasks, and the pilot has 12 task clusters. Predeclare task strata, balanced/randomized arm order, cold/warm cache policy, maintenance attribution, timeout handling, and exclusions in the hashed tool-policy/selection manifests. Retain failed and timed-out attempts; do not silently replace them with a successful run.

The concrete held-out planning proposal is **at least 30 distinct held-out tasks across 3 repositories (10 tasks each) × 3 arms × 3 repetitions = at least 270 task-run observations**, separate from the 12 development tasks. With one paired contrast per task after aggregating its three repetitions, a two-sided 95% paired t confidence interval has planning half-width `t(29, 0.975) / sqrt(30) ≈ 0.37` times the paired task-level standard deviation, under independent task clusters and approximately normal paired contrasts. This is a relative precision justification, not a power guarantee for a 25% token reduction or for acceptance noninferiority. The pilot must estimate that standard deviation and show whether this width is useful in token-ratio units. The proposal is **unregistered** until the actual held-out task identities/count, three-repository split manifest, three repetitions, assumptions, and rule below are frozen before any pilot/tuning run. If the pilot shows inadequate precision, keep the fixed sample size and report inconclusive efficacy; any larger study requires a new preregistration or a genuinely prespecified blinded reestimation rule, never an effect-driven increase.

Choose the held-out sample size from an explicit precision/power calculation at the task-cluster level using a conservative variance assumption or independent prior measurements. Record the assumptions and their limitations before the pilot. If the plan permits learning variance from the pilot, preregister a **blinded** sample-size reestimation rule, statistic, target precision/power, minimum/maximum task count, and stopping rule before collection. Preselect and hash the complete held-out reserve pool before tuning. Apply that rule once using variance without arm-effect estimates, before tuning or unblinding held-out outcomes; retain the original specification and record a dated, separately hashed amendment with the selected task count and pilot-variance evidence. Do not retrospectively alter `preregisteredAt`, choose a favorable sample size from observed effects, or treat synthetic success as a power estimate. If variance or coverage cannot support the frozen plan, report the limitation and withhold efficacy claims.

## Primary metric and decision policy

The proposed directional target is a **25% reduction in total disjoint processed tokens per accepted task run**, with no decrease in measured acceptance. It is an experimental target, not a measured result or an existing release gate. The existing release accuracy threshold is unrelated.

For each arm, sum all four disjoint token categories over **every** initial attempt, retry, repair, failed task, and attributed maintenance item in the frozen task set, then divide by accepted task runs. Do not average only successful attempts or compute an unweighted average of per-task ratios. If there are no accepted tasks, leave the ratio undefined (`null`), even when complete total usage is known. A zero baseline token ratio also leaves percentage reduction undefined. Report acceptance/error counts beside the token ratio; a descriptive token reduction does not override worse outcomes.

Maintenance includes experiment-attributable context/graph refreshes, indexing, synchronization, preparation, and repair work. Assign each maintenance usage event to exactly one task run in its arm according to the frozen allocation rule, retaining a unique event ID. Shared maintenance is charged once per arm, never once per accepted task; conservation of the external maintenance ledger must be reviewed. If absence was measured, record an empty maintenance ledger with evidence. If maintenance or attempts are incomplete, mark the run incomplete rather than asserting complete accounting. The evaluator detects duplicated supplied IDs; it cannot discover undisclosed attempts or verify an operator's completeness assertion.

Report measured cost and elapsed task-run latency separately. Cost uses actual measured amounts and an explicit currency for each attempt/maintenance item; do not infer cost from total tokens or assume cached tokens have the uncached price. Missing cost remains unavailable. Run latency is measured wall-clock duration including its retries/repairs, not a sum of overlapping child durations. Separately retain maintenance duration in its evidence; the reported task-run latency does not pretend to include shared preparation time. Never substitute latency or cost for missing usage.

## Telemetry normalization and evidence boundaries

`usageFromTelemetry(sample)` is the concrete bridge from the telemetry summary into the run-record usage shape. It requires both `accounting.complete === true` and `scope.status === 'complete'`, all four available categories, and a safe exact `accounting.totalTokens` equal to their sum. Parent-only telemetry can contain a category total, but the adapter cannot make it complete. Authorized child manifests are explicit; no transcript-directory scan is permitted. Use an item ID for each distinct complete session/attempt; do not charge a child separately after including it in its parent's complete sample.

The fixture-backed host normalization rules are:

- Claude `input_tokens` excludes separate `cache_creation_input_tokens` and `cache_read_input_tokens`; keep uncached input, cache writes, cache reads, and output disjoint.
- In the supported OpenAI/Codex shapes, input includes cache reads. Subtract cache reads exactly once to obtain uncached input; a separately unsupported cache-write category is explicitly `not-applicable` (zero) only where the host contract supports that interpretation.
- Output already includes reasoning output where provided; never add reasoning tokens again.
- Missing counters, unsupported host shapes, or anonymous logical message IDs make accounting incomplete. Repeated snapshots of a logical call are reconciled to final cumulative usage rather than summed as separate calls.

These are synthetic schema/normalization tests, not live-host proof. `reported`, `not-applicable`, and `unavailable` remain distinct in telemetry; the evaluator adapter maps a justified not-applicable zero to an available zero. Unknown categories and incomplete scope stay unavailable. Aggregate token values must remain safe integers; overflow leaves totals unavailable. Do not add an inclusive input or total counter alongside the four normalized categories.

## Collection and analysis

Store only normalized usage, fixed identities/hashes, measured check commands/results, outcome counts, timing, and evidence references. Do not store raw prompts, responses, private transcripts, secrets, or provider credentials in run records. Source/selection/artifact hashes prove consistency against supplied artifacts; the evaluator does not authenticate data provenance. Independent evidence review remains necessary.

Run every task/seed/repetition in all three arms under identical frozen conditions. Required checks are fixed in each task. Acceptance requires all checks to exit zero without timeout and zero measured regression, missed-change, unnecessary-change, clarification-error, and missed-context counts. Check/outcome evidence hashes refer to retained measured evidence, not generated success labels. Label development and pilot records correctly and keep them out of held-out analysis.

Use `evaluateEfficiencyRuns(spec, records)` or:

```sh
node scripts/evaluate-efficiency-runs.mjs --spec frozen-experiment.json --results measured-runs.json
```

The specification and each run conform to the schemas documented in [RECORDS.md](RECORDS.md). The CLI exits zero only for complete token measurement; this exit code is not a benefit, accuracy, or release verdict. Missing arms, duplicates, mismatched identities/conditions/artifacts/specification hashes, unavailable usage, incomplete scope, or unsafe aggregate counts prevent complete token comparison. Cost and latency retain independent availability. Full token measurement with zero accepted tasks is still a complete collection with an undefined efficiency ratio.

Describe task-level variation and paired comparisons before any interpretation. Any future confidence interval or power analysis must cluster by task, honor the frozen split and decision policy, and retain negative results. The current evaluator intentionally performs no significance test and issues no efficacy claim. Preserve all original/amended specifications, baseline manifests, normalized records, check evidence, allocation ledgers, and descriptive reports for review. An efficiency report never replaces native-host, authorization, safety, production, or release qualification.
